# G4R 工程复审记录

基准为 `25c26b9c560a36ee2d4df321614bf96c36c4f475`（G3）和 `9fd09b1084018f431f6ba6908862372c6ebd2c8e`（G4）。版本保持 `4.0.0-alpha.4`。使用 Windows 本机、隔离曲库和受控音频。

## A. WASAPI 时钟、设备与数字精度

`output.rs` 此前用 `endpoint_clock.take()` 完成一次观测后就丢弃同一流的 `IAudioClock2`。现在保留接口，活动流每约 200 ms 读取一次，检查 `GetDevicePosition` 的 `S_OK` 与非零 QPC。共享设备的绝对设备位置用于诊断。歌曲位置仍取当前**流**的 `IAudioClock` 单位，经 `GetFrequency` 换算为帧，再由带 `seq/runId/epoch` 的 PCM 标记定位。预卷和补充静音不当作歌曲帧。`GetStreamLatency` 仅记录端点报告值。

`StreamClock` 先校验 QPC 新鲜度，超过 100 ms 或来自未来的样本直接丢弃。对乱序观测使用 Padding 并保留继续接收正常观测的能力。新鲜且同频的流时钟倒退仍判为重置，直到新设备流。设备时钟值停住 75 ms 且 Padding 显示正在消费时临时回退，可信观测恢复后重新采纳。原生 QPC 修正最多 10 ms，Renderer 插值最多 55 ms，均受已提交歌曲帧约束。暂停、seek、缓冲、恢复和桌面歌词沿用现有输出时间合同。 [流时钟说明](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition) · [设备时钟说明](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock2-getdeviceposition)

Windows Senary Audio 的共享流以 48 kHz / Float32 运行，取得 57 次流时钟报告及同一设备会话三次递增的设备观测（1,739、12,298、22,862 帧）。44.1 kHz / 32 位整数独占流报告 56 次 Padding 位置，成功暂停、跳转、到 2.65 秒触发 EOF 并释放。最终原生程序在 AirPods Pro 上用合成 ALAC 复跑，共享 48 kHz / Float32 有 57 次流时钟报告及 3 次递增设备观测；独占 48 kHz / 16 位以零流位置开始，转 Padding 后取得 58 次运行位置。两路均通过暂停、短文件 seek、EOF 和释放。G4 的启动无消费在本轮真实端点未再出现，继续以故障注入覆盖。恢复测试覆盖同设备／默认设备重开、独占无消费转共享、过期事务撤销、解码下溢、进程中断和单次 EOF。真实环回、物理 DAC 延迟与漂移、USB 拔插和跨端点独占争用仍缺实测。

数字测试验证 16/24/32 位整数、24-bit packed、24-in-32、边界与低有效位，以及重采样、声道变化、静音、增益、硬件偏移和淡变。精确输出只标在实际符合源采样率和声道布局、精度足够、独占且没有软件缩放和淡变的提交区间。该证据到达 WASAPI 输入。跨驱动没有足够证据支持事件驱动或更短预卷，保留活动约 3 ms 轮询、空闲较长等待、独占约 60 ms 目标缓冲及 300 ms 锁定预卷。

G4 与 G4R-A 各 16 轮的模拟设备释放确认 P50 / P95 为 58.75 / 60.30 → 57.91 / 59.86 ms，保持远低于旧 G3 约 302 ms 的 P95。10 秒暂停各测一次，原生进程 CPU 增量 15.6 → 46.9 ms，两边重复位置消息均为零，采样句柄稳定在 110。该次数不足以判断稳定 CPU 变化。

## B. ALAC、扫描与写入验证

锁定 Chromium 缺少直接 ALAC 解码能力。Symphonia 的 MP4 探测未给出该编码的有效位深，`decode.rs` 通过该版本 ALAC 配置读取位深供 Hi-Fi 和 PCM 流共享。普通播放按曲库授权的文件及版本请求虚拟 PCM WAVE。`electron/alac.cjs` 将任意字节区间对齐到样本，原生程序按索引跳到目标包并裁剪，最多 4 个运行中的解码或探测子进程、64 个探测头缓存，利用管道背压以及 Range 取消关闭。流程不要求整首转码或长期保留完整 PCM。现有 HTMLMediaElement、音量、空间声场和时钟继续消费同一媒体源。Hi-Fi 直接读 ALAC 并沿用输出事务，工坊选择文件后凭短期令牌读取。

真实端点探针复现了短 ALAC 已全部预读后跳转失败。Symphonia 0.6.1 的 MP4 解复用器在 EOF 后仍可以更新样本索引，但后续读取需要一个尚未耗尽的 atom 迭代器。Hi-Fi 在这一路径重新打开解复用器，从索引定位后只裁剪当前包，保留原播放授权与设备事务。

| 场景 | 实际结果 |
| --- | --- |
| 16／24 位合成 ALAC、AAC 对照 | 分别生成带 96×96 封面、无封面、内嵌逐字 TTML、普通歌词及无歌词。实际扫描正确识别编码、无损、位深和封面。原生 ALAC 完整 PCM 及多个非对齐的 seek 范围与 FFmpeg 逐字节一致。 |
| 普通输出、时钟、ALAC 续播 | Electron 实测音频到 Web Audio 图、定位到临近结尾、专辑由 EOF 切到 24 位 ALAC。核对 GET、HEAD、不对齐 206、416 和中止后继续读取。24 位 ALAC 左右声道频率分别通过图内检查，空间聆听室音量减半为 −6.01 dB，静音及退出路由均通过。 |
| Hi-Fi | 通过应用驱动模拟独占、共享、短 ALAC 预读到 EOF 后 seek 和切回普通。模拟独占捕获的 PCM 与目标区间原生解码样本逐字节相同。Windows AirPods Pro 共享与独占通过合成 ALAC 播放探针。 |
| 分析、工坊、导出 | 节奏与响度分析成功，工坊从曲库与原生文件选择器加载 PCM，实时预览成功，导出 MP4 用 FFprobe 确认含 AAC 音轨。逐字与辅助轨使用同一解析入口。 |
| 用户的 `01. SugarCrash!.m4a` | 隔离副本识别为 44.1 kHz / 16 位 / 双声道、80.081 秒，有内嵌封面及 `©lyr` TTML。完整 14,126,208 PCM 字节与 FFmpeg 一致。通过 Electron 普通播放、seek、播放中改写 TTML 并从当前时间恢复。写回副本 PCM 再次比对，原始文件整档 SHA-256 一致。原样本及其歌词不属于测试资产。 |
| 标签和身份 | 16 位 ALAC、AAC、用户副本逐项回读新歌词，所有 `mdat` 与非目标 `ilst` 项原始字节摘要保持不变（用户副本涵盖 24 个非目标项）。重扫保留条目 ID 和已经完成的分析。用户样本的作曲、发行日期、版权、ISRC、UPC 已读入曲库。普通 `©lyr` 保持空行、纯时间戳、段落和原始文本。外部修改后提交旧编辑会被拒绝，文件哈希不变。 |

MP4 写入使用同目录唯一临时副本，验证目标字段和媒体、元数据完整性，然后确认源文件未被外部更改再原子替换。已存在的外置 `.ttml` 优先并在该处保存；否则从内嵌读取，经文件标签设置写回 `©lyr`。用户改用 LRC 时沿用明确选择。格式或权限不足导致写入失败时保留原件。标签刷新按 `TAGS_V` 执行，保留数据代次，不触发全资料清理。编辑内容的持久化和显示先后顺序明确，播放只等待同一文件的写入完成。

虚拟 WAVE 当前受 RIFF 的 4 GiB 上限约束。20／32 位与多声道 ALAC 在代码中有格式路径，尚缺逐格式 Chromium 样本。自动分析仍有 64 MiB 原始文件与 128 MiB PCM 预算，显式工坊和导出可以完整解码；G6 接续有界分析与复用。仅改写 `©lyr` 的安全哈希不等于 G5 音频身份算法。未对普通 ALAC 的分钟级内存、真实 DAC 位一致性或物理端点做外推。

## C. G0–G4 架构核对

| 阶段 | 证据与处理 |
| --- | --- |
| G0 | 保留听见新声、旧声结束、视觉就绪及 CPU、GPU 测量口径。G4R 将两条 LRC/TTML 运行时循环移除，严格检查仍在。G6 与 G9 的另外八条历史环留在原处。 |
| G1 | 配置锁、清理事务、应用目录范围、断点恢复和正式版/兼容版规则继续通过隔离行为测试。仅更新曲库的标签扫描版本。G5 可以在同一受管边界分别存放用户资料与缓存。 |
| G2 | `coordinator.ts` 负责队列、输出和代次。`player.ts` 同时编排优先级、Session、应用覆盖、UI 投影和文件写入，仍是后续可拆的边界。G4R 仅把写入释放、序列化与重启保留在同曲目的事务里，不给编辑器直接操作输出的权力。 |
| G3 | 普通流式元素、自动分析、工坊和导出有各自的资源周期。原生 ALAC 解决浏览器能力不一致，不扩大其他格式的后台完整解码。`Session` 等待字体、分析结果及规划的成本留给 G6/G7。 |
| G4 | 流时钟和端点诊断分开。独占的有效流观测仍依赖驱动行为，Renderer 只沿当前输出插值。采用可信度检查的回退应作为正式功能持续验证。 |

`Engine.frameAt()` 每帧调用 Cadenza 的 `cameraAt` 后把 `cf` 放进共享 `RenderFrame`。Folia 独立构图，但视图、背景和合成依然可消费此帧，具有跨风格影响的结构风险。`Engine.frame()` 在收到音频 EOF 后还允许短暂推进视觉片尾，仍由协调器独立推进队列。G7 用固定时点和复杂样本对照跨风格影响，并明确定义歌曲时间、片尾时间和画面交接。G8 继续验证工坊与导出的组合一致性。G9 处理完整预设、布局可替换及旧菜单限制。对应目标统一登记在 [项目方向](DIRECTION.md)，历史四分页和初次移植的原样构图做法分别归档在 [风格系统](STYLE-SYSTEM.md) 与 [Folia](FOLIA.md)。

## 回归验收

- Windows Electron 构建和 Rust Release 构建通过。TypeScript、Prettier 和 393 项单元及架构断言通过。资料生命周期、隔离和范围协议 17 项通过。
- 7 项 Rust 单测、13 项原生模拟专项和原有模拟播放测试通过。最终构建 45 秒模拟长播的消费速度为墙钟 1.020001 倍，2,026 个观测的歌曲时钟与提交帧映射误差小于 1 帧。受控设备重开故障注入约 828 ms 恢复。
- 经典桌面 76 项、空间 28 项、Hi-Fi 桌面 19 项和 3 组播放生命周期回归通过。流式专项的 12 组格式或声道样本均通过。45 分钟 WAV 首次图内信号前累计读 1,310,720 字节，主动断供冻结时钟，seek 触发局部读取，停止后读流全部关闭。
- ALAC 专项覆盖上表格式、响应、PCM、seek、分析、导出与标签写入。物理端点和线上平台的未验证边界见各自章节。
