# G6 节奏分析与后台资源

播放、视觉和曲库分析使用不同的生命周期。播放时钟给出当前位置，节奏分析产生文件时间上的观察数据，导演按当前播放时间、歌词和风格解释数据。曲库音频、歌词和基础视觉可以先呈现。等到完整分析完成，播放器按会话修订通过 `Session.stage()` 接入同一份 Map。

## 输入与计算

- `electron/library.cjs` 批准带文件修订的曲库音频请求。`analysis-pcm.cjs` 复用原生解码器，按块发送最多 4096 帧的交错 Float32 PCM。请求取消、清缓存和应用退出会释放解码进程。结束帧只在解码正常完成后写出。
- Opus 和裸 AAC 由现有 Mediabunny 与 Chromium 解码能力提供 PCM。读取采用 Range、2 MiB 缓存和单路并发。保留源媒体时间，容器时间戳的毫秒级舍入按连续采样处理，较大空隙显式表示为静音。
- `file-analysis.worker.ts` 一次读取同时计算响度和节奏所需特征。DSP 重采样保留滤波边界和绝对相位，FFT 跨块保留重叠，曲级统计及动态拍点从紧凑特征计算。最多累计 120 万谱帧，持续时间约 200 分钟。特征和最终结果随曲长增长，PCM 工作集由块和模型窗口决定。
- Beat This! 提供拍点与强拍候选，HTDemucs 可选地分离鼓与人声，DSP 保留谱通量、响度、起音和段落推断。模型窗口最多 30 秒，前后各 2 秒上下文，槽位按源采样坐标归属，接缝附近的重复拍点被抑制。与完整输入相比，窗口局部归一化和模型上下文可能影响推理结果。无模型时，自动模式可退回 DSP。显式神经模式在模型无法运行时报告不可用。
- `RhythmAnalysis` v4 的 `beatEvidence` 明示检测结果。等待分析、静音及缺乏足够节拍证据的信号通过 `RhythmMap` 提供空格线和静态拍相位。临时等待数据不可提交缓存。分离出的鼓点、人声及拍上重音继续保留，Folia 直接读取同一份 `accents`，DSP 路径保留其风格信号适配。非曲库的无声创作仍可选择显式 BPM 网格。
- Beat This! 上游以 22.05 kHz 单声道计算 log-mel，网络输入为最长 1500 个谱帧，上游会裁掉窗边并拼接预测。HTDemucs 上游对分块输出做带重叠的加权叠加。Cadenza 继续使用 Folia 移植的模型推理和拍上特征实现，外层流式 PCM 窗口负责资源上限和绝对媒体坐标。神经网络原始推理和音乐事件融合是两层。 [Beat This!](https://github.com/CPJKU/beat_this/blob/main/beat_this/inference.py) · [Demucs](https://github.com/facebookresearch/demucs/blob/main/demucs/apply.py) · [Folia 对照](FOLIA.md)

## 任务及缓存契约

主进程仍用 G5.5-R 的后台任务入口和状态。Renderer 同时接受一个曲库分析工作，当前请求可抢占其他内容，别名共用内容任务。导出暂停曲库分析。清理和手动重分析同时撤销旧提交许可与活动任务。一个已经进入 ONNX 的请求可能需要收尾，单次 PCM 窗口有上限，结果受取消信号和缓存许可约束。模型空闲回收沿用现有 Worker 和 utility process 生命周期。

曲库只维护一份通用内容索引。`db.derived` 按 G5 验证的 `AudioContentId` 索引。分析按实际配置、数据版本及兼容签名命中。兼容签名包括算法和时间基准版本，以及对应模式可使用的模型 SHA-256。纯 DSP 键不受分离或推理设备配置影响。缓存是 gzip 压缩的头和 JSON 正文，正文不再嵌套转义，SHA-256 校验 JSON 正文。缓存写入沿用原子替换、文件修订、内容代次及全局清理代次检查。正文不包含原始 PCM、权重、频谱矩阵或中间推理张量。响度单独以内容和版本索引，清理沿用统一的 `clearCaches`。

标签、歌词、封面及曲目位置修改后，重新验证相同内容时可继续复用缓存。修订不一致期间旧结果没有提交授权。损坏、旧版本或模型兼容签名不匹配的结果需要重算，旧索引和用户资料继续沿用 G5 的迁移机制。本轮保持安装版本和资料代次，避免将分析缓存升级变成用户资料断代。

## G5.5-F 补修

- 历史 `preferLrc` 等实际来源枚举后再迁移，按原优先顺序选择存在的外置 LRC 或内嵌 LRC。已保存的显式选择优先。在更早构建里已经落成显式 `sidecar:lrc` 的值，若无来源标记，无法确定它是用户选择还是历史自动迁移。
- AI 译文在 TTML 由原生语言轨保存，在非 TTML 明确选择独立译文源或支持的 FLAC `LYRICS_TRANSLATION` 字段。按时间锚合并时保留空行、时间戳、原词和无法识别的结构。重复或歧义锚点要求先人工处理。结果先进入现有编辑草稿，实际应用受源修订及编辑权限校验。
- 按 AI 服务保存模型、语种、额外指令和超时偏好。临时改动留在本次草稿，显式保存才更新该服务和默认服务。凭据继续由现有主进程凭据库管理。

## 验证边界

Windows 长音频探针在隔离目录生成素材，记录播放状态、跳转、完整缓存落地、实际 PCM 协议字节和 Electron 进程私有内存。测试中 Web Audio 图或模拟 PCM 信号与播放状态分别报告。没有测量物理输出延迟，也没有用点击脉冲对照替代真实音乐人工标注。

这是同一 Windows 主机上的单次、每档独立测试。图内信号采样与合成音频自身每半秒一次的脉冲有关。全部结果就绪包括同内容副本、短 FLAC 和短 Opus。每档恰有两次原生解码完成，长 WAV 与其副本合用一次，Opus 由 Chromium 解码。每档重启后命中缓存，原生分析解码启动数为零。长曲末段五个拍点与合成时间基准的差值均为约 −3 毫秒。单次内存数据包含播放器、窗口、Worker 和暂态的正常开销，不能等同于模型内存或磁盘物理读取量。

G5.5-F 对同一 15 分钟文件以旧文件预算跳过分析，播放状态报告耗时为 375 ms，G6 此轮为 360 ms。两个数字只用于核对同一探针的播放状态，未取得足够样本评估 P50/P95 或起播变化。G6 初次 45 分钟实现耗时 42.28 s。复用整数延迟相关、缩减历史扫描后，本轮耗时 22.19 s，仍需重复样本拆分各自收益和系统调度波动。

内置合成基准覆盖固定速度、3/4、变速、鼓点定位、安静及持续音。真实 WebGPU 模型经 Windows SwiftShader 验证，128 BPM 合成乐曲的全输入参考读数为 128.3 BPM，拍点 P90 误差为 17.5 ms，强拍最差偏差 25 ms。使用 `STREAM=1` 的对照中，分块与完整输入在相同区间均命中 73 个标注拍点（±70 ms），28 秒邻近窗口交界的拍点连续。HTDemucs 的独立短段读到 9 个底鼓、5 个军鼓、21 个钹点，无鼓前奏未触发律动。软件后端的全输入拍点与分块分别耗时 76 s 和 92 s，短段打击乐分离耗时约 383 s。不能外推真实 GPU 或 ONNX 提供程序的吞吐，也未证明长曲分块分鼓在所有后端与原全曲结果等价。自动模式可在推理预算用尽时使用 DSP。
