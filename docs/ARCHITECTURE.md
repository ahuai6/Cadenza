# Cadenza 架构

本机音乐库播放器：音乐库与高保真播放、节奏分析、多格式歌词、特效歌词、正在播放页、歌词工坊与视频导出、经典与空间两种界面，各部分同样重要、彼此咬合。这份是总览：每个部分做什么、数据怎么流、边界在哪。各部分的规则细节在 `docs/parts/`；它们是由这份文档 3.5.0 之前的内容拆出来的，改程序时改对应的那一份。

日常、编辑模式与空间玩法共享本地曲库。桌面编辑由命令层和主进程共同检查权限。主窗口 preload 提供按次调用的歌词搜索与受控 AI 接口。凭据只在主进程解密，译文须经当前 TTML 草稿审核和现有字段写入事务。 [歌词服务](G55-F.md)

G7 在同一渲染进程中让原生字形、Folia 舞台批次、网格和滤镜共享二维 WebGL2 设备。原生导演和 Folia 风格分别拥有镜头、构图与转场，使用同一媒体时间、节奏、歌词和图层契约。G8 让实时播放和工坊消费同一视觉输入，导出采用独立的 Engine 与参数快照，继续提交同一种 `RenderFrame`。流式分析在完整结果写入前分段供给实测特征，Folia 的动态节拍状态随视觉实例释放。 [G7 渲染基础](G7.md) · [G8 实现与证据](G8.md)

## 平台

- **Electron + React + TypeScript（strict）**。渲染与导出需要确定性：Electron 自带固定版本的 Chromium（WebView2 随系统变）。纯逻辑模块（节奏、歌词、导演）不依赖 DOM，能在 Node 直接单元测试。
- **高保真输出**是独立的 Rust 进程 `native/cadenza-audio`。它管理 WASAPI 独占和共享流、自适应采样率及设备恢复，主进程通过管道发送命令并接收带代次的观测结果。
- **神经网络节奏**在桌面版由 ONNX Runtime 在 utility process 执行（`electron/infer*.cjs`；Windows 用 DirectML），没有时退回浏览器 WebGPU，再退回内置的信号分析。

## 分层

```
core ──► text ──► lyrics ──┐
  ├────► rhythm ───────────┼──► director ──► render ──► engine ──► app（React：views/ 经典、space/ 空间）
  ├────► theme ────────────┤        ▲           ▲
  └────► i18n              └──► folia ──────────┘   （Folia 的风格与背景：在 director 旁、render 之下）
electron（主进程：音乐库、设置、窗口、Hi-Fi、原生推理）   native（Rust 播放核心）
```

现行目录边界由 `tests/unit/arch.test.ts` 检查。它用 Vite 的 TypeScript AST 与模块解析识别静态导入、重导出、类型引用、字面量动态导入及别名。运行时图排除纯类型依赖。计算生成的路径与 IPC 流程另用行为测试。

- 每个模块只能引用它下层的模块；`lyrics` 用自己的最小接口 `BeatGrid` 读节拍，不引用 `rhythm`。
- 目前界面经 `src/engine/index.ts` 访问引擎下层，另可访问 `core`、`theme`、`i18n`。4.0.0 的目标是按播放、视觉和共享契约设置入口，迁移时同步更新测试。
- `app` 里：`views/` 与 `space/` 互不引用；逻辑层（`state.ts`、`bridge.ts`、`playback/`、`actions/`、`commands/`、`settings/`）不引用任何画面；只有 `bridge.ts` 碰主进程；空间的场景只经过 `space/bind.ts` 读写 Cadenza。
- 组件样式不写字面的圆角与时长（只用 `styles/tokens.css`）。

G0 记录了 10 条运行时循环边。G4R 将共用的歌词分词移入 `lyrics/words.ts`，移除 `parse ↔ ttml` 的两条运行时边及测试豁免。`AlbumLine ↔ Library` 以及 `Effect / Modals / Settings` 留到界面治理，`rhythm/index ↔ rhythm/stream` 随分析调度治理。保留现有层级检查，按职责迁移消除豁免。

## 时间模型

- **文件位置**以秒计。桌面进度与控制使用 `playback.time()`，在准备、暂停、缓冲和拖动时保持目标或最后所见位置，运行时读当前输出。歌词时间为文件位置减去 Session 的 `audioStart`。改变歌词偏移只重排视觉时间，不会重启音频。
- **普通输出（阶段 1，`alpha.6` 起）**是自建的 PCM 管线：原生核心 `--play-pcm` 以歌曲自己的采样率解码为立体声 Float32（Opus、裸 AAC 及原生读不了的格式由 Worker 里的 Mediabunny 解码），`src/engine/stream/pcm-feed.worker.ts` 直接把样本交给 AudioWorklet `pcm-worklet.ts`，界面主线程不经手音频。Worklet 用一个跨歌连续的窗函数 sinc 滤波器重采样到输出采样率（同采样率逐位拷贝），所以串联的下一首从上一首最后一个采样之后开始，没有间隙，也没有滤波器边缘。暂停、停止和定位有 6 ms 包络，非专辑曲尾 1.6 秒淡出和音量平衡作用在每首歌自己的样本上。歌曲时间由 Worklet 报告的「音频上下文帧 → 歌曲位置」锚点加上下文的输出时间戳求出，不再估算输出延迟。暂停或断流时冻结，定位开一条新流。
- **Hi-Fi（G4/G4R）**用 `IAudioClock::GetPosition` / `GetFrequency` 将流时钟单位换算为端点流采样率下的帧，并用同一 QPC 时间域检查观测新鲜度。只有 `S_OK` 的新鲜观测可采用。时钟停滞且 Padding 仍显示进展、时钟重置或位置与已提交范围冲突时，使用已提交帧减 Padding 的估计，标明来源。共享模式可另外连续采样 `IAudioClock2` 的设备帧，约 200 ms 一次。独占模式或接口不可用时省略这份诊断。`GetStreamLatency` 与设备帧均仅用于诊断。消费进度和物理 DAC 发声时间各自测量。
- 输出队列分别记录预卷静音、提交帧与歌曲样本的对应关系，每段标记带有解码代次 `seq` 和运行代次 `runId`。每次新设备流另有 `epoch`，Electron 子进程另有 `processEpoch`。Renderer 只接受当前运行的时间，可沿当前已提交的歌曲帧插值至多 55 ms。暂停、缓冲、恢复和 seek 按运行状态冻结或重新锚定。桌面歌词沿用同一时间和剩余插值预算。菜单使用界面单调时钟，离线导出使用帧时刻，无音频工坊可使用项目时钟。
- `evaluate(plan, t)` 是导演的求值入口。预览与导出的完整画面还涉及媒体帧、字体、特效状态和合成路径，使用逐帧对照验证一致性。

## 播放生命周期（G2–G4）

```text
经典 / 空间 / 媒体键 / 任务栏 → 播放命令 → PlaybackCoordinator
                                           ├→ 撤销上一个请求 → 停止旧输出
                                           ├→ prepare → start → 输出确认 → EOF → 队列策略
                                           └→ 音频可用后安排视觉准备 → Session → Engine
```

- `coordinator.ts` 只依赖通用状态工具。队列项的 `key` 标识一次出现，`id` 标识曲库条目。换曲提升代次，暂停、拖动和跳转撤销正在运行的回调。目标条目、播放意图、正在输出的条目和视觉就绪各有独立含义。失效资源只能被释放，无法取得起播授权。
- 快照订阅同步执行。发布缓冲与 EOF 快照后，在提交后端指令或自动续播前重新确认授权。单纯位置改变由时钟和 `tick` 驱动进度与歌词，场景修订事件用于实际视觉改动。
- `outputs.ts` 适配普通 PCM 输出（`pcm-output.ts`）和原生 Hi-Fi。两路提供准备、开始、暂停、停止、文件时间和运行、缓冲、结束、错误事件，以及可选的 `running()`：已被无缝接上、正在发声的输出由协调器直接置为播放中，不经过缓冲状态。普通输出接入原有 Web Audio 音量与空间声场图。退出 Hi-Fi 等待主进程确认旧子进程结束。
- Hi-Fi 设备变更先释放旧流，再由当前配置事务提交新设置。原生端协商实际模式、格式和端点并报告回退。失效时冻结在最后确认消费的歌曲位置，关闭旧流，依次延时 250、500、1000 ms 有限重试。恢复如需更改采样率或声道布局，从冻结点按新格式解码。默认端点可跟随系统，指定端点失效后允许回退，已稳定运行的回退端点保留至下一次释放或重配置。EOF 要等最后一个标记覆盖的音频帧消费完毕，且匹配当前 `seq/runId`。
- 若设备报告启动成功，但已提交的帧连续 1 秒没有消费进展，按流故障处理。独占流先关闭，再尝试共享，沿用当前歌曲位置与播放授权。短暂出现消费进展不立即恢复重试预算。
- Hi-Fi 在同一轮界面操作内合并已经撤销的准备请求。原生端限制同时退出的解码器数量，名额受限时只保留最新的前台等待项并撤销旧歌输出，后台预读让出名额。
- **无缝续播**：确定的下一首（非随机模式）在当前歌曲播放 1.5 秒后预读并串联。普通输出由 Worklet 在同一渲染循环里接续；Hi-Fi 由原生核心在下一首格式与当前设备流相同时，于同一条流里接续（`chain` 命令、`joined` 事件，上一首的结束在设备消费到接缝时才报告）。格式不同需要重开设备时照旧有间隙。候选失效时撤销，单曲标签写入会释放当前输出及对应候选，Hi-Fi 另等原生关闭确认。
- **MP4 无缝信息**：Symphonia 0.6.1 读取但不应用编辑列表。`native/cadenza-audio/src/mp4gapless.rs` 读取音轨的 `elst`（退回 iTunes 的 `iTunSMPB`），解码时去掉编码器预置延迟和尾部填充；普通播放、Hi-Fi 和曲库分析共用，因此 MP4 的分析缓存兼容签名另加了 `mp4-edit-list-v1`。
- **Hi-Fi 时钟锚点**：原生位置报告带读取时刻的 QPC（`at100ns`），渲染端测出 QPC 与 `performance.now()` 的偏移（最短往返），以读取时刻而非消息到达时刻为锚；时间戳不可信时退回到达时刻。
- `player.ts` 将播放状态投影给界面，并安排当前 Session。进入新请求时移除旧歌词和 MV，先显示新歌曲的基本信息。视觉数据、字体和规划完成后按请求代次接入，失败独立报告。构建最多同时一份，等待中的工作只保留最新一份。已提交的浏览器解码、字体或分析工作可能继续收尾，下一步检查取消信号。
- `Session` 消费时长、节奏数据和可显式调用的离线 PCM 加载方法。普通播放只保留流式 PCM，不持有整曲。G6 曲库工作通过独立的有界 PCM 流产出节奏与响度，复用 G5 内容索引及 G5.5-R 后台任务。工坊和导出在明确请求时完整解码。 [节奏分析架构](G6.md)
- **ALAC（G4R）**在曲库解析实际编码后，由主进程授权媒体源交给 `electron/alac.cjs`。原生 Symphonia 以样本区间逐块解码并交付虚拟 WAVE，保留有效位深与通道布局。普通播放与 Hi-Fi 现在都由原生核心直接解码原文件，虚拟 WAVE 仍供工坊导入等媒体元素使用。分析、工坊与导出可显式读取同一解码能力。工坊本地导入通过原生文件选择器签发短期令牌，Renderer 无需知道文件路径。见 [G4R 复审记录](G4R.md)。
- 桌面 `Engine` 从协调器读时间；工坊仍可用独立时间轴。歌曲最后一帧与队列尚有下一首是两件事。视觉可以继续做短过渡或在队列停下后显示尾卡，音频队列不会等待它。

## 一帧的数据流

```
音频档 ──► 节奏分析（worker／原生推理，缓存）──► RhythmMap ──┐
歌词档 ──► parseLyrics ──► 分词与合词 ──► 歌词模型 ──────────┼──► Session
外观＋风格（theme/style.ts，每首歌各自绑定）─────────────────┘        │
                                                                    ▼
                         导演 plan（worker）→ ScenePlan   或   Folia 引擎（engine 字段）
                                                                    │
时钟 t ──► Engine.frameAt(t) ──► RenderFrame ──► renderer：背景 → 歌词 → 特效 → 转场的样子 → 字幕 → 屏幕特效
```

## 歌词来源与后台任务

歌词内容身份由曲目、实际存储字段和可校验修订构成。播放器消费已选来源或临时预览，编辑器保留原始文档并修改明确的节点。编辑命令经主进程权限及修订检查，标签写入复用播放文件释放事务。音频内容身份继续用于节奏和响度缓存。

主进程负责目录扫描、媒体索引与读写权限，Renderer 负责分析任务的实际执行状态。活动入口显示真实扫描、指纹和分析阶段，失败、跳过和暂停可独立查看。运行状态和任务结果的测试边界见 [G5.5-R](G55-R.md)。

## 主进程（`electron/`）

应用进程在加载主服务前由 `profile.cjs` 按构建阶段、程序版本与数据代次检查资料。Windows 先验证路径，再在原有用户资料根上取得 Electron 单实例锁。清理或迁移成功后才读设置、连接曲库与启动窗口。已知旧资料的退役与清理由持久化的事务记录恢复，Chromium 单实例锁与应用控制记录独立于被处理的数据条目。发行阶段和测试入口见 [维护](MAINTENANCE.md#400-启动与数据断代)。

- `main.cjs`：窗口、托盘、协定（`cadenza://` 提供封面、音频、字体、模型）、媒体键、程序自己的设置（`settings.json`，默认值档 `settings.defaults.json` 由纲要产生）。
- `library.cjs`：扫描、标签（node-taglib-sharp）、封面、歌单、`audioKey`（略过标签区块的音频哈希，改标签不会重新分析）、歌词写回标签（临时副本再改名）。
- `audio.cjs`：与 Rust 高保真播放核心的管道（页面只给歌曲 id，看不到路径）。
- `desk.cjs`：桌面歌词的独立窗口。
- `infer.cjs`／`inferHost.cjs`：原生推理的 utility process。
- `preload.cjs`：暴露给页面的 API；页面只经过 `src/app/bridge.ts` 使用。新增能力三处都要改：`ipcMain.handle` → `preload.cjs` → `bridge.ts`。

受平台保护的文件（`.ncm`、`.qmc*`、`.kgm` 等）只列出并标示，绝不解密、不播放。
