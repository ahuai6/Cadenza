# 测试

4.0.0 重构使用 [3.6.0 隔离基线](BASELINE-3.6.0.md)。其中记录了同一提交的回归结果、普通与模拟 Hi-Fi 的独立时间点及硬件 GPU 帧数据。后续阶段比较时保留同样的环境、素材和测量口径。

## G3 普通流式输出

技术路线为 `HTMLAudioElement` → `MediaElementAudioSourceNode` → 现有 Web Audio 增益和空间路由。锁定的 Electron 45.1.0 / Chromium 156 实测支持下表格式，六声道的不同频率在图内逐一对齐。现有格式矩阵没有发现必须用完整解码回退的条目。`AudioWorklet` 加 PCM 环形缓冲可以支持自定义调度与更严格的缓冲控制，但还需要解复用、解码、声道与 seek 实现。Mediabunny 加 WebCodecs 可作为将来验证特殊格式或样本级续播的候选。当前采用已有浏览器管线，工坊和导出继续按需完整解码。 [媒体元素源](https://developer.mozilla.org/en-US/docs/Web/API/MediaElementAudioSourceNode) · [Web Audio](https://www.w3.org/TR/webaudio/) · [Mediabunny](https://mediabunny.dev/guide/introduction)

| 格式 | Windows Electron 实测配置 |
| --- | --- |
| MP3 | 44.1 kHz、VBR、立体声 |
| AAC | M4A 尾部索引、MP4 前置索引的 48 kHz AAC，以及 44.1 kHz 的裸 ADTS |
| FLAC | 96 kHz / 24 bit 立体声，48 kHz / 5.1 六路独立信号 |
| WAV | 48 kHz / 24 bit 立体声，以及用于流式探针的 48 kHz / 16 bit 长文件 |
| Ogg | 44.1 kHz Vorbis，48 kHz Opus |
| WebM | 48 kHz Opus 和 Vorbis |

另用无保护 ALAC/M4A 对照，锁定版本的媒体元素与旧 `decodeAudioData()` 均报告无法解码。该样本未触发额外回退。裸 ADTS 的曲库扫描可能没有时长，播放器用媒体管线已取得的时长约束正在播放歌曲的分析预算。

- `node --test tests/file-response.cjs` 验证 GET / HEAD、单区间 206、无效与不满足区间的 416、打开的文件与响应一致、错误、请求中止和消费者取消。多个区间统一返回 416。`cadenza://media` 仍通过曲库 ID 授权，受保护文件不可读取。普通输出的 URL 固定当次文件长度与修改时间，后续区间重开时校验。已经缓冲的旧字节可能继续播放，大小和修改时间相同的替换仍需 G5 的内容身份处理。 [Electron 协议](https://www.electronjs.org/docs/latest/api/protocol)
- `node tests/streaming-desktop.cjs --space` 使用生成文件、独立 profile 和真实 Electron。按需要在 PowerShell 设置 `$env:CADENZA_STREAM_SOAK_SECONDS='60'`，增加连续播放的内存、进程与 CPU 采样。真实路径使用主进程读流字节和关闭记录、Web Audio 分声道 FFT、播放快照、Electron CDP 的 JS Heap 与进程指标。Chrome DevTools 和 Playwright CLI 的隔离 HTTP 页面只补充 Range 和交互证据。
- 常规曲库分析与视觉的临时完整解码使用 64 MiB 文件预算和 128 MiB 的 PCM 估算上限。超过预算，可直接播放并使用已有分析或基础视觉。节奏分析任务保留现有策略，已提交给 Chromium 的解码仍会收尾。超长音频的渐进式分析和任务资源调度由 G6 处理。工坊和有声导出是显式离线操作，有各自完整解码的内存成本。
- 保持独立的旧信号结束、新信号出现与视觉计划三个时间点。`tests/baseline/playback.cjs` 保持 3.6.0 原口径。`tests/baseline/continuity.cjs <快照目录> <输出目录>` 在 G2 及后续版本测量 20 次前后段频率不同的 seek、预读后的手动选择以及真实图内自然续播间隙。两个输出目录均需是 `CADENZA_BASELINE_ROOT` 下不存在的直接子目录。图内间隙与解码器、缓冲区、图调度和采样窗口相关，物理端点另测。

G3 20 次专辑续播中有 19 次落在同一 FFT 采样窗口，另一次观测间隔为 13.9 ms。这个探针不能判定样本级无缝或真实端点停顿。压缩格式的编码器首尾填充、浏览器解码调度和输出端点行为均需独立验证。

在 45 分钟、518,400,044 字节的立体声 WAV 上，受控慢读时首次图内信号出现前主进程仅读取约 1.57 MB。人为断供时文件时钟冻结在约 4.01 秒，解除断供后继续。seek 到 2690 秒触发了从字节 516,456,448 开始的请求，停止后原先三个读流都关闭。连续播放 60 秒的后 50 秒内，强制 GC 后的渲染端 JS Heap 为 19.00–19.04 MB。采样中的渲染进程私有内存约 250–321 MiB，包含媒体、字体和渲染资源。连续播放采样中渲染进程 CPU 为 1.6%–3.7%，这些数据用于定位开销，单独分离浏览器媒体缓冲的占用仍需 Chromium 内部指标。

另用同一个 10 分钟、115,200,044 字节 WAV 做一次配对测量。G2 首次图内信号为 1514.9 ms，主进程已读完整文件。G3 为 48.9 ms，彼时已读 2,031,616 字节。播放约 10 秒后的渲染进程私有内存为 747 → 233 MiB，扣除各自播放前的值，增量为约 310 → 49 MiB。JS Heap 为 17.53 → 16.68 MB。采样时各 Electron 进程的工作集之和为 1111 → 709 MiB，共享页可能重复计入。从选择曲目到该采样点，渲染进程累计 CPU 时间增加 18.7 → 4.7 秒。这组结果包含渲染与自动分析预算的影响，只代表这次大文件配对样本。

Windows 本机通过类型和格式检查、单元与架构测试 40 套共 391 项、范围协议 5 项、资料生命周期 12 项、经典桌面 76 项、空间 28 项、模拟 Hi-Fi 桌面 19 项及 Rust 模拟设备 32 项。两路 G2 生命周期回归通过。G3 专项通过全部 11 组格式、断供恢复、快切与已打开媒体的连续替换、播放中文件变更与释放。实际 Electron 空间模式也验证了房间输入、半音量约 -6.01 dB、静音与耳机路由恢复。经典套件覆盖桌面歌词、Folia、MV、独立工坊时钟和带 AAC 音轨的导出。Hi-Fi 模拟复用了 G2 已构建的原生程序，G3 的 Rust 源码保持原样。

## G0–G2 工具接入后复审

- 固定提交的 G0 播放和 GPU 探针已在 Windows 隔离目录复跑。播放探针现在把采样窗口内缺少的指标记为失败，避免仅靠其余样本得出通过结论。频率、阈值、采样窗口、硬件含义和历史基线均保持原口径。GPU 报告的 CPU 同步提交与浏览器帧间隔分别采样，端点执行时间和显存属于 G7 的实机工作。
- G1 单测新增已进入清理阶段、且外部模型目录指向隔离区的合成用例。旧代码会继续清理，修复后保留文件和待恢复记录。目录联接、文件占用、进程中断、单实例和兼容迁移继续走已有隔离用例。
- G2 单测加入同步订阅者抢占起播和自然续播、拖动时输出身份、AudioContext 暂停时的位置保持，以及包含重复曲目的三轮随机播放。实际 Electron 专项套件继续验证两路输出、视觉阻塞、连续撤销与自然续播，新增 Hi-Fi 写入标签期间的暂停和跳转、停止后取消视觉等待，以及拖动时视觉通知数量。标签竞态通过主进程受控写入复现，经典桌面套件继续验证真实写入。
- 暂停状态下在 Electron 打开播放页和队列，对 `787b24b` 与复审构建施加 240 次拖动更新加一次提交。两端均收到 241 次位置更新，最终位置均为 6.25 秒。播放器投影的订阅通知、Engine 视觉通知和视觉修订计数都从 241 次降到 0。React 提交次数和整机 CPU 降幅需要单独采样。

## G2 播放生命周期

- `tests/unit/playback-coordinator.test.ts` 用可控后端验证请求代次、重复队列项、暂停时的准备、跳转、失败重试、自然续播以及多次撤销后的资源释放。架构测试验证协调器不能依赖平台桥或视觉层。

## 渲染测试的性能门槛（3.5.0 重新校准）

这个环境的浏览器以软件绘图，比显卡慢数倍，而且快慢随机器而变：以毫秒为门槛时，同一份代码在慢的机器上就会失败。所以 `perf` 先量一段**不含 Cadenza 代码的固定画布工作**（渐层、带阴影的文字、缩放复制、读回一个像素）当这台机器的速度，再把每帧的时间换成它的倍数：

- 3.5.0 量到的倍数（三次在 5% 内）：liquid 9.4、gothic 12.5、cover 11。
- 超过基准 25% 才失败。基准要更新时，在 `tests/render.cjs` 的 `BASE` 改数字并写明版本与原因。

性能结论只能来自实机；这里的数字只看「有没有变慢」。

## Folia 对照

参考页（`tests/folia-ref/`）在 Folia 的 checkout 里建置，用真正的 Pixi 8 与 Folia 自己的 React 背景；Cadenza 这边用 harness（`npx vite build --mode harness`）。参考页需要的套件照 Folia 的 lockfile 版本另外装进 checkout 的 `node_modules`（在 checkout 里直接 `npm install` 会被它的 git 依赖挡住）。

```
node tests/folia-stage-compare.cjs <checkout> <输出>                                # 舞台：文字、图形、模糊、滤镜、遮罩
node tests/folia-compare.cjs <checkout> <输出> sonnet,tempera 0.5                    # 全曲逐格（静止）
node tests/folia-compare.cjs <checkout> <输出> sonnet-beat,tempera-beat 2.1          # 播放中、拍点特效打开
node tests/folia-bg-compare.cjs <checkout> <输出>                                   # 五种背景（静止）＋动态（几何图形、莫奈漂移）
```

做法与注意：

- 两边的 `Math.random` 换成同一个固定种子（Folia 有几处细节用真乱数）。每格在全新状态下画。
- **拍点对照**：两边装同一份合成拍点清单，在虚拟时钟（`performance.now` 被换掉）上以每秒 60 步走过时间点前 1.5 秒，再画那一格。
- **动态背景对照**：Folia 的几何图形与莫奈漂移是浏览器动画，暂停后设到同一时刻（`BG.seek`）；几何图形的版面由同一个种子产生（`BG.seed`）。参考页用 1920×1080：Cadenza 把 Folia 的 CSS 像素当成 1080p 页面的大小。
- 软件 WebGL 偶尔掉格，脚本会重画；磁盘配额用完时浏览器会直接崩溃，先清空间。

3.5.0 的结果（平均色差，越小越像）：

| 对照 | 结果 |
| --- | --- |
| 五种背景（静止） | 0.00%–0.14% |
| 通用背景的几何图形（1、7、13.5、29、61 秒） | 0.02% |
| 莫奈的漂移（6、17、40 秒） | 0.25%（0.5 秒时 0.44%，是淡入） |
| 商籁，静止／播放中 | 粗略重合率 95%／95%；拍点反应两边逐格一致（开关拍点造成的变化两边完全相同） |
| 凝彩，静止／播放中 | 粗略重合率 98%／99%；剩下的差异来自 Folia 在播放状态另以墙钟时间驱动的色块动画，不是拍点 |
