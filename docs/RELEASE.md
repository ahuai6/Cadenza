## Cadenza 2.17.5

**「きゃきゃきゃ……」一段卡住、背景變黑：找到根本原因並修正**

第三份日誌顯示 2.17.4 的備援有效，整段沒有任何一幀出錯。對照前兩份日誌後，原因已經確定：
- 封面外觀會在部分詞外畫「歌詞框」。鏡頭規劃最後有一道「把歌詞框保持在畫面內」的步驟，它會直接修改平滑後的鏡頭路徑，而且只改 x、y 和遠近。這正好就是日誌裡變成 NaN 的那三個值。
- 這一段裡有一個歌詞框離正在唱的字太遠，所以被放棄。被放棄的那一刻，剛好沒有任何字正在唱（長詞的尾音不算在「正在唱」內）。這一步因此在「沒有任何東西要框」的情況下照樣去計算，結果是：
  - 取景範圍變成 +∞ 到 −∞；
  - 拉遠的量算成 log(0)，平移的量算成 ∞×0，也就是 NaN。
- 這個 NaN 經過平滑，擴散成 2.27 秒的鏡頭路徑，所以三份日誌的時間段一模一樣。
- 之前在規劃階段加的檢查沒抓到，是因為它們在這一步之前就已經檢查完了。

修正：
- 沒有任何東西需要框住時，這一刻不做修正。
- 算出的修正量不是有限數字時一律不套用。
- 新增測試重現這個狀況：舊程式會產生 NaN，新程式不會。
- 2.17.1–2.17.4 加的各層防護與除錯日誌都保留。現在這段的鏡頭回到平常平滑的移動（2.17.4 的備援改用未平滑的規劃位置，這段的移動可能稍顯生硬）。

## Cadenza 2.17.3

**「きゃきゃきゃ……」一段卡住、背景變黑：日誌找到了原因所在**

你傳來的除錯日誌記錄到：
- 從 112.97 秒到 115.23 秒，鏡頭規劃出的位置與遠近（x、y、z）不是數字（NaN）。這正是鏡頭移向那個長詞的時候，其他數值都正常。

- 這解釋了效能資料為什麼沒有異常：每幀都在跑，只是一開始就出錯中止了。

這次的修正：
- **鏡頭規劃**：每個停點的位置、遠近、角度、縱深都會檢查；有不是數字的，這個停點改照前一個停點的取景，跟隨步驟也逐步檢查。
- **平滑後的路徑**：任何一個取樣點不是數字，就沿用前一點，不會再被平滑擴散成兩秒多。
- **繪製**：計算鏡頭速度的那一步也加了檢查，NaN 不會再讓整幀中斷。
- **日誌**：發生上述修正時，會把那個停點的完整資料（哪幾個字、各自的位置大小、時間、取景框、前一個停點）記成「PLAN WARNING」，也寫進檔頭。下一份日誌就能直接指出 NaN 是怎麼產生的，我會把根源修掉。

這些數值來自歌曲的節奏分析（拍點、響度、層次）。存檔時，分析裡的 NaN 會變成 null；拍點也可能前後倒序。我手上沒有你那首歌的分析，所以這次做了三層防護：

- **每一幀檢查**：鏡頭、畫面律動、節奏取樣裡只要有一個值不是數字，這一幀改用上一個正常幀的數值畫，並記下是哪個欄位。
